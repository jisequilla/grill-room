# Decisions: Depth and technical level before the grill

Generated by the Grill Room export from this session's settled design tree.

## Decisions

<a id="level-scale"></a>
### The technical-level choices

- **Decision:** Three: builder / technical but not building / not technical
- **Why (interviewer's case):** Separates wording (plain or technical) from decision-making (owner chooses or leaves it). Costs a third branch the prompt must honour consistently.
- **Recommendation note (interviewer's):** Wording and who decides are independent axes, and the middle value is a real person: someone who reads technical cards fine but wants the builder to pick the technology. Three values cover the behaviours without a free-text interpretation step.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** `one-idea-owner-technical-level-trait` (knowledge/product/decisions/one-idea-owner-technical-level-is-a-trait.md:25-27)

<a id="mid-session-change"></a>
### Whether depth or level can change after round 1

- **Decision:** Both editable at any round, applied from the next round
- **Why (interviewer's case):** Treats them as the interviewer's settings, which they are; already-asked cards stay, later ones adapt. Costs a UI affordance outside the opening and a prompt that must take the current values each turn.
- **Recommendation note (interviewer's):** The prompt builder is called every turn anyway, so applying the current values from the next round is cheap, and neither value is stored with the idea it judged the way readiness is. Locking only creates a reason to abandon a session and restart.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** `readiness-only-before-first-round` (grill-room/server/readiness.ts:1-8)
- **Owner's choice for the depth action:** while a turn is working after the interview has started, a depth change is refused (`turn-in-progress`), so a running turn never finishes at the old depth over the change. The technical level cannot be cleared once set; it is changed between the three levels only.

<a id="depth-cadence"></a>
### Depth is asked per session, not per owner

- **Decision:** Per session, asked each time an idea is opened
- **Why (interviewer's case):** The same owner wants a PoC for one idea and a full spec for another, so the value belongs with the idea. Costs one extra question at every session start.
- **Recommendation note (interviewer's):** Depth describes the idea, and the owner's own words framed it as a per-idea choice. One question at session start is cheap, and it keeps a single source of truth on the session next to readiness.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** `one-idea-owner-technical-level-trait` (knowledge/product/decisions/one-idea-owner-technical-level-is-a-trait.md:25-27), `scope-use-case-is-capture-point` (knowledge/product/use-cases/readiness/scope-how-deep-to-grill.md:24-26)

<a id="depth-scale"></a>
### The depth choices

- **Decision:** Three: proof of concept / first working version / full spec
- **Why (interviewer's case):** Each step has a distinct done-criterion (does it work at all, can people use it, is nothing left to the builder's guesswork). Costs one more choice to explain.
- **Recommendation note (interviewer's):** Three steps map to three different stopping rules for the interviewer, which is what depth exists to change. Two collapses the most common case, a usable first version, into one of the extremes.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** `scope-use-case-is-capture-point` (knowledge/product/use-cases/readiness/scope-how-deep-to-grill.md:24-26)

<a id="depth-downstream"></a>
### Whether depth changes the spec, tickets or handoff

- **Decision:** Interview plus the spec check's bar: at PoC depth, more is allowed to be left to the builder; at first working version, a gap only the builder would notice (a scale limit, an operational setting, an internal timeout) is not a finding
- **Why (interviewer's case):** Keeps artifacts honest about what the owner chose not to settle. Costs a depth input to the spec check and wording in the spec that names the depth.
- **Recommendation note (interviewer's):** The spec check already looks for what a builder would have to decide alone; without depth it would nag a PoC owner about gaps they chose to leave. Tickets derive from the spec, so they follow without their own branch.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [The depth choices](#depth-scale)

<a id="depth-shapes-interview"></a>
### What each depth step changes in the interview

- **Decision:** Done threshold plus which branches open: lower depth skips scale, edge-case and operations branches
- **Why (interviewer's case):** Shorter grill from the first round and a done point that matches. Costs the prompt naming which branch kinds belong to which depth.
- **Recommendation note (interviewer's):** Depth is most felt in which questions never get asked; a done threshold alone still spends the owner's early rounds on branches they did not want.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [The depth choices](#depth-scale)

<a id="at-first-working-version-are-the-scale-a-2780456e"></a>
### At first working version, are the scale and edge-case branches opened or skipped?

- **Decision:** Edge cases opened, scale and operations skipped
- **Why (interviewer's case):** A first version must survive real users' odd inputs but not load or on-call. Costs a prompt that distinguishes edge-case branches from scale ones.
- **Recommendation note (interviewer's):** Edge cases are what users hit on day one; scale is what they hit on day one hundred. First working version is the step between, so it takes edge cases and leaves scale and operations to full spec.
- **Origin:** user · accepted recommendation
- **Depends on:** [The depth choices](#depth-scale), [What each depth step changes in the interview](#depth-shapes-interview)

<a id="at-first-working-version-what-must-be-se-79b98f09"></a>
### At first working version, what must be settled before the interviewer proposes being done?

- **Decision:** Every user-facing flow and its data settled; technology and operations may be builder's calls
- **Why (interviewer's case):** Matches what a usable first release needs and gives a checkable rule. Costs the prompt classifying each open branch as user-facing or not.
- **Recommendation note (interviewer's):** The step exists for a version real people can use, so done means every flow a user touches and the data behind it are settled, while anything the builder can decide without the user noticing may stay a builder's call.
- **Origin:** user · accepted recommendation
- **Depends on:** `builders-call-is-owner-set-aside` (knowledge/interview/language/builders-call.md:22), [The depth choices](#depth-scale), [What each depth step changes in the interview](#depth-shapes-interview)

<a id="level-storage"></a>
### Where the owner's technical level is stored

- **Decision:** New owner profile table; sessions reference it
- **Why (interviewer's case):** Gives the trait a real home and makes 'once at first setup' literal. Costs a new table, an identity question (who is the owner when there are no accounts), and a migration.
- **Origin:** interviewer · another offered option
- **Depends on:** `one-idea-owner-technical-level-trait` (knowledge/product/decisions/one-idea-owner-technical-level-is-a-trait.md:25-27), `scope-use-case-is-capture-point` (knowledge/product/use-cases/readiness/scope-how-deep-to-grill.md:24-26)
- **ADR-worthy:** yes
- **Consequences:** Commits depth and level to columns on the sessions table next to readiness, with the server reading the previous session to pre-fill level. Rules out a per-owner entity for now; if accounts are added later, the level must be lifted out of sessions.

<a id="level-change-writes-back"></a>
### What a mid-session level change updates

- **Decision:** Profile only: sessions read the profile live, no session copy
- **Why (interviewer's case):** One place holds the trait, and a correction fixes every later session too. Costs the ability to grill one idea at a different level than usual, and a profile edit mid-session that affects other open sessions.
- **Recommendation note (interviewer's):** The trait describes the person, and a mid-session change is almost always a correction, not an exception for this idea. Reading the profile live keeps the data model you chose honest: sessions reference the owner rather than duplicating them.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** `one-idea-owner-technical-level-trait` (knowledge/product/decisions/one-idea-owner-technical-level-is-a-trait.md:25-27), [Whether depth or level can change after round 1](#mid-session-change), [Where the owner's technical level is stored](#level-storage)
- **ADR-worthy:** yes
- **Consequences:** Commits sessions to carrying no technical-level column; the prompt builder reads it through the owner reference every turn. Rules out per-session level exceptions without a later schema change.

<a id="once-the-interviewer-has-proposed-being--05e72964"></a>
### Once the interviewer has proposed being done and a spec has been synthesized, can depth still be changed, and if so is the spec and its check re-run at the new depth or left as generated?

- **Decision:** Still editable; the spec, its check and tickets are marked stale and must be regenerated to reflect the new depth
- **Why (interviewer's case):** Keeps one rule for editing and reuses the existing stale marking rather than silently diverging artifacts. Costs a regeneration the owner must trigger.
- **Recommendation note (interviewer's):** The app already treats artifacts produced from earlier state as stale rather than locking inputs. A depth change after done is a real case, raising from proof of concept to full spec, and it should reopen the frontier for the next round and flag the spec and tickets for regeneration instead of locking the control or regenerating unasked.
- **Origin:** user · accepted recommendation
- **Depends on:** [Whether depth or level can change after round 1](#mid-session-change), [Whether depth changes the spec, tickets or handoff](#depth-downstream), [What each depth step changes in the interview](#depth-shapes-interview)
- **Owner's choice for the depth action:** both `done-proposed` and `confirmed` return to interviewing; leaving `confirmed` marks the spec not current, and with it the tickets and the consistency check. Nothing is regenerated.

<a id="owner-identity"></a>
### How an owner is identified for the profile table

- **Decision:** Real sign-in (accounts) backing the profile. The agent-native framework already ships Better Auth login/signup, enabled unless AUTH_DISABLED is set, so the profile row keys off the signed-in user; no new authentication layer is built.
- **Origin:** interviewer · own answer
- **Depends on:** `one-idea-owner-technical-level-trait` (knowledge/product/decisions/one-idea-owner-technical-level-is-a-trait.md:25-27), [Where the owner's technical level is stored](#level-storage)
- **ADR-worthy:** yes
- **Consequences:** Commits the schema to an owners table keyed by a chosen name and a nullable owner reference on sessions, with no authentication. Rules out treating the level as private, and makes adding real accounts later a migration of owners rather than a fresh start.

<a id="existing-sessions-owner"></a>
### What happens to sessions created before owners existed

- **Decision:** Assign them all to a single migrated owner created from today's technical user
- **Why (interviewer's case):** Every session has an owner and the existing user's history stays theirs. Costs assuming all past sessions belong to one person.
- **Recommendation note (interviewer's):** Until now there was one real user, so attributing past sessions to them is true in practice and avoids a nullable owner reference everywhere else in the code.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Where the owner's technical level is stored](#level-storage), [How an owner is identified for the profile table](#owner-identity)

### Once login is on, which signed-in Better Auth user should take over the migrated sessions, and when: the first user who signs in, a named email, or nobody?

- **Decision:** The first user who signs in after the migration inherits them, once
- **Why (interviewer's case):** Needs no configuration and matches reality on a single-owner install. Costs a wrong hand-off if someone else happens to sign in first on a shared deployment.
- **Origin:** user · another offered option

<a id="profile-table-shape"></a>
### Where the level sits relative to the Better Auth user

- **Decision:** Separate owner profile table keyed by the auth user id
- **Why (interviewer's case):** Keeps framework-owned auth tables untouched, so Better Auth upgrades and its migrations never collide with app fields. Costs a join and a row that must be created lazily on first setup.
- **Recommendation note (interviewer's):** Better Auth generates and migrates its own tables; app fields on them are the first thing a framework upgrade breaks. A one-row profile per user id is cheap and leaves room for later owner traits.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Where the owner's technical level is stored](#level-storage), [How an owner is identified for the profile table](#owner-identity)
- **ADR-worthy:** yes
- **Consequences:** Commits the schema to an owner_profiles table with the auth user id as its key and sessions referencing that user id. Rules out app fields on Better Auth tables and makes every level read a join or a second query.

- **Recommendation note (interviewer's):** Sharpening does not run for every session and readiness has already judged by the time its view shows, so only a step at session creation reaches every owner before anything is judged.

<a id="readiness-reads-depth"></a>
### Whether readiness lowers its bar at lower depth

- **Decision:** Readiness reads depth and scales what counts as ready
- **Why (interviewer's case):** Fewer false warnings at low depth. Costs a depth input to readiness and the judgment now depending on a value the owner can change.
- **Recommendation note (interviewer's):** Readiness only warns, so the cost of a wrong call is low, but sending a PoC owner into Sharpening for a full-spec gap is exactly the over-grilling this idea is meant to stop.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** `readiness-warns-never-blocks` (grill-room/server/readiness.ts:5-7), [The depth choices](#depth-scale), [Where the two questions are asked in the flow](#capture-placement)

<a id="depth-change-rejudges-readiness"></a>
### Whether changing depth re-runs readiness

- **Decision:** Before round 1: re-judge automatically; after round 1: judgment stays as it was
- **Why (interviewer's case):** The judgment stays true to its inputs in the only window where it can act, and the existing lock is untouched. Costs one more readiness call when depth is changed early, and a judgment that can be stale about depth once rounds exist.
- **Recommendation note (interviewer's):** Readiness exists to decide whether Sharpening runs, and that decision is only live before round 1, so re-judging there is the whole value and re-judging later has no consumer. The stored judgment should record the depth it was made at so the staleness is visible.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** `readiness-only-before-first-round` (grill-room/server/readiness.ts:1-8), [Whether depth or level can change after round 1](#mid-session-change), [Whether readiness lowers its bar at lower depth](#readiness-reads-depth)
- **Owner's choice for the depth action:** only a session with a stored judgment is re-judged; one never judged, or whose judgment an idea edit cleared, gets the new depth and no model turn. A re-judge that fails keeps the new depth and the cleared override, and the error is surfaced.

- **Recommendation note (interviewer's):** The judgment field exists to show which depth the verdict assumed; writing a depth it never saw defeats that. These sessions already have rounds and will not be re-judged, so a null with a short label costs nothing beyond one branch in the panel.
- **Origin:** user · accepted recommendation

- **Decision:** Store the change and re-judge when the turn ends

- **Decision:** Clear the override; the new judgment decides again
- **Why (interviewer's case):** The override answered a judgment that no longer exists. Costs the owner re-confirming if the idea is still not ready at the new depth.
- **Recommendation note (interviewer's):** The override was a reply to a specific judgment at a specific depth. A new depth makes a new judgment, and the owner can override again in one tap if they still want to.

- **Recommendation note (interviewer's):** A wrong level is the costliest misjudgment in this design, and showing the current value is the cheapest correction point. Pre-filled, it costs no extra click when it is right.

<a id="technical-questions-for-non-technical-owner"></a>
### Who answers technology questions the owner cannot

- **Decision:** Interviewer asks in outcome terms with a recommendation; owner accepts it or leaves it to the builder
- **Why (interviewer's case):** Keeps builder's call owner-initiated and lets the owner weigh what the choice means for them (cost, speed, lock-in) without naming technologies. Costs prompt work to translate each technical choice into consequences.
- **Recommendation note (interviewer's):** The owner can still judge consequences even when they cannot judge technologies, so ask in those terms and make 'Leave it to the builder' the recommended answer when the choice has no owner-visible consequence. That reuses builder's call unchanged and never fabricates a decision.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** `builders-call-is-owner-set-aside` (knowledge/interview/language/builders-call.md:22), `one-idea-owner-technical-level-trait` (knowledge/product/decisions/one-idea-owner-technical-level-is-a-trait.md:25-27)

<a id="do-sharpening-s-cards-also-take-the-owne-7e84439c"></a>
### Do Sharpening's cards also take the owner's technical level for wording and recommendation shape, or does Sharpening read depth only?

- **Decision:** Sharpening takes both depth and level, same rules as the grill. Its depth section is its own text: the grill's scope rule for each depth without the rules about proposing `done`, which Sharpening never does
- **Why (interviewer's case):** A non-technical owner meets Sharpening first, so plain wording matters most there. Costs passing one more input into a prompt that already takes depth.
- **Recommendation note (interviewer's):** Sharpening is the first thing a new non-technical owner sees; it should obey the same level rules as every later card, and the prompt builder already takes level, so the cost is one argument.
- **Origin:** user · accepted recommendation
- **Depends on:** `sharpening-pre-round-one-in-session` (knowledge/interview/decisions/sharpening-rewrites-the-idea-until-ready.md:22-24), [Whether readiness lowers its bar at lower depth](#readiness-reads-depth), [What each technical level changes in the cards](#level-shapes-cards)

<a id="when-a-depth-change-during-sharpening-re-9a07c0e6"></a>
### When a depth change during Sharpening re-judges the idea as ready, does Sharpening end at once or finish its current round first?

- **Decision:** Finish the open round, then stop
- **Why (interviewer's case):** The owner's in-progress answers are kept and seed decisions. Costs one more round of cards after the idea was already judged ready.
- **Recommendation note (interviewer's):** Sharpening rounds are one to four cards, so finishing is cheap, and the owner can already press 'Grill it as is' to stop early. Keeping the round intact avoids a partial round in the history.
- **Origin:** user · accepted recommendation

<a id="queued-depth-change-semantics"></a>
### How a depth change queued behind a working turn behaves

- **Decision:** Latest value wins; one re-judge after the turn ends; the control shows 'applies when this step finishes'
- **Why (interviewer's case):** Simple rule, one readiness call, and the owner is told why nothing changed yet. Costs a small pending indicator in the UI.
- **Recommendation note (interviewer's):** Readiness only reads the current depth, so earlier queued values have no consumer; one re-judge with the latest value is all that is needed, and a short pending note keeps the control honest.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [If depth is changed before round 1 while a turn is working, is the change refused, or stored and readiness re-judged once the turn ends?](#if-depth-is-changed-before-round-1-while-9d91f1eb), [When a depth change during Sharpening re-judges the idea as ready, does Sharpening end at once or finish its current round first?](#when-a-depth-change-during-sharpening-re-9a07c0e6)
- **Owner's choice for the depth action:** a queued depth is applied when the readiness action ends, after its judge (never after its scout turn), followed by one re-judge; and when the first round opens (after its proposal turn, or with none when decisions are already pending), where it is written and the 'Grill it as is' record cleared, with no re-judge because the interview has started. A turn that fails leaves the queued depth in place.

<a id="when-depth-changes-after-the-interviewer-456365fd"></a>
### When depth changes after the interviewer has proposed done but before any spec is synthesized, does the frontier reopen for the next round in the same way?

- **Decision:** Yes: the done proposal is withdrawn and the frontier reopens at the new depth
- **Why (interviewer's case):** Same behaviour as after a spec, minus the stale marks, so there is one rule. Costs withdrawing a done proposal the owner may have been about to accept.
- **Recommendation note (interviewer's):** The done proposal was computed at the old depth; raising depth means branches the interviewer never opened. Withdrawing the proposal and recomputing the frontier is the only way the new depth has an effect before a spec exists.
- **Origin:** user · accepted recommendation
- **Depends on:** [Whether depth or level can change after round 1](#mid-session-change), [What each depth step changes in the interview](#depth-shapes-interview), [Once the interviewer has proposed being done and a spec has been synthesized, can depth still be changed, and if so is the spec and its check re-run at the new depth or left as generated?](#once-the-interviewer-has-proposed-being--05e72964)

<a id="when-the-first-real-user-inherits-the-pl-0768fd04"></a>
### When the first real user inherits the placeholder's sessions, does a technical level stored on the placeholder profile (set while login was off) move to that user's profile, or is it discarded with the row?

- **Decision:** Move it: the inheriting user's profile takes the placeholder's level if their own is still empty
- **Why (interviewer's case):** The same person who set it locally is almost certainly the one signing in, so their setup survives. Costs a small merge rule when the user already has a level.
- **Recommendation note (interviewer's):** The hand-off already assumes the first sign-in is the person whose sessions these were; carrying the level along is the same assumption and spares a second setup. If the user already has a level, theirs wins.
- **Origin:** user · accepted recommendation
- **Depends on:** [What a mid-session level change updates](#level-change-writes-back), [Once login is on, which signed-in Better Auth user should take over the migrated sessions, and when: the first user who signs in, a named email, or nobody?](#once-login-is-on-which-signed-in-better--a9380634), [Who inherits migrated sessions when login is switched off](#migrated-sessions-under-auth-disabled)

<a id="when-the-profile-has-no-level-yet-is-the-a7d790b3"></a>
### When the profile has no level yet, is the setup step shown with nothing selected or with 'not technical' preselected, and does creating the session with that preselection save it to the profile?

- **Decision:** Nothing selected; creating the session without a pick leaves the profile empty and the interviewer uses the skip default
- **Why (interviewer's case):** The profile only ever holds a choice the owner made, so the step keeps asking until they pick. Costs the step reappearing with an empty level on every session until then.
- **Recommendation note (interviewer's):** The profile should hold only what the owner said. Leaving it empty keeps the skip default as a runtime assumption rather than a recorded fact, and the pre-filled step on later sessions is exactly the correction point already chosen.
- **Origin:** user · accepted recommendation
