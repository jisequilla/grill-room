# Decisions: Delivery loop: gauntlet stages, PR evidence and mutation testing

Generated by the Grill Room export from this session's settled design tree.

## Decisions

<a id="merge-danger-gate"></a>
### What a one-way door in Merge danger changes in the main session

- **Decision:** One-way door requires the owner's typed confirmation before merge
- **Why (interviewer's case):** Matches the launch rule already in place. Costs a pause on every migration PR.
- **Recommendation note (interviewer's):** A one-way door should stop the main session and ask, the same way a launch does. The section then has a consumer.
- **Origin:** interviewer · accepted recommendation

<a id="mutation-role"></a>
### Mutation result: gate, report, or gate only on acceptance-covered lines

- **Decision:** Gate on acceptance-covered lines, report elsewhere
- **Why (interviewer's case):** Ties the gate to the promise the PR already makes: each acceptance line has a named test, so a survivor on those lines proves the named test is weak. Survivors on other changed lines stay informational. It costs a mapping step from acceptance line to line ranges, which the builder must write into the PR body.
- **Recommendation note (interviewer's):** The Evidence section already names a test per acceptance line, so the reviewer has a list of lines the PR claims are tested. A survivor there is a proven gap in exactly the test the builder quoted, and that is the finding a human reviewer found by hand in gr-2f9.7. Survivors elsewhere stay as report lines so the pilot can tell you how noisy a full gate would have been before you commit to one.
- **Origin:** interviewer · accepted recommendation
- **ADR-worthy:** yes
- **Consequences:** Commits the loop to a mapping from acceptance lines to changed line ranges in every PR body, and makes a surviving mutant on those lines a blocking finding by rule. It rules out a plain score threshold as the gate and makes a later move to a whole-diff gate a template change rather than a new mechanism.

<a id="mutation-runner"></a>
### Who runs Stryker: the tests lens, a separate mutation critic, or a deterministic workflow step

- **Decision:** Deterministic workflow step feeding the tests lens
- **Why (interviewer's case):** Stryker runs once, in the script, with a fixed command and cap, and its JSON report is passed to the tests lens template as filled input. Costs a change to ticket-build-review-loop.js and means a hand-run loop without the workflow has to run the command by hand.
- **Recommendation note (interviewer's):** Run Stryker once in the workflow script between build and review, with the cap enforced by the script, and pass the survivor list into the tests lens reviewer's template. The reviewer's job is to turn survivors into file:line findings and to check the builder's equivalence claims, not to run a tool. The reviewer template documents the command so a hand loop can do the same.
- **Origin:** interviewer · accepted recommendation
- **ADR-worthy:** yes
- **Consequences:** Commits the saved workflow to a non-agent step with its own cap and failure mode, and makes the tests lens template take a survivor list as input. Rules out lens-local mutation runs and means review done outside the workflow has one more manual command.

<a id="equivalent-mutant-handling"></a>
### Who may declare a mutant equivalent and how it is recorded

- **Decision:** Reviewer declares it in the verdict with the mutant quoted; builder may propose in the fix round
- **Why (interviewer's case):** Keeps the judgment with the adversarial party. Costs reviewer tokens on each claim.
- **Recommendation note (interviewer's):** The reviewer owns the equivalence call and writes it into the verdict; nothing persistent is committed during the pilot.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Mutation result: gate, report, or gate only on acceptance-covered lines](#mutation-role), [Who runs Stryker: the tests lens, a separate mutation critic, or a deterministic workflow step](#mutation-runner)

<a id="mutation-scope"></a>
### How the diff scope is expressed to Stryker

- **Decision:** Changed line ranges per file from git diff
- **Why (interviewer's case):** Exactly the lines the PR touches, so every mutant is about this PR. Costs a small script to turn hunks into Stryker ranges and the ranges shift if the builder reformats.
- **Recommendation note (interviewer's):** Line ranges from the diff are the only scope that keeps the run inside the cap on this suite, and they give the acceptance-line mapping something concrete to point at. A short script in the workflow turns hunks into ranges.
- **Origin:** interviewer · accepted recommendation

<a id="acceptance-range-mapping"></a>
### How the builder maps each acceptance line to line ranges

- **Decision:** Each Evidence entry lists path:start-end ranges next to the named test
- **Why (interviewer's case):** Machine-comparable and visible in the PR body. Costs the builder a few lines per acceptance item and goes stale if the diff moves.
- **Recommendation note (interviewer's):** Explicit ranges in the Evidence entry make the gate auditable from the PR alone and give the workflow step a trivial comparison. The reviewer still re-runs the test, so a stale range shows up as a mismatch, not a silent miss.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Mutation result: gate, report, or gate only on acceptance-covered lines](#mutation-role), [How the diff scope is expressed to Stryker](#mutation-scope)

<a id="mutation-score"></a>
### Mutation score threshold, if any

- **Decision:** Record the score, never gate on it
- **Why (interviewer's case):** Gives the benchmark a column to compare across the three pilot tickets. Costs nothing in the loop but invites people to read it as a target.
- **Recommendation note (interviewer's):** Record the percentage Stryker prints so the benchmark has it, but let the per-survivor rule from the role decision do the gating. Percentages on diff-sized mutant sets are too coarse to block on.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Mutation result: gate, report, or gate only on acceptance-covered lines](#mutation-role)

<a id="nit-bead-filer"></a>
### Who files the nits bead: the workflow's last step or the main session after merge

- **Decision:** Workflow returns nits in its result; main session files the bead right after merge
- **Why (interviewer's case):** Respects the rule that merge and close stay in the main session and avoids a bead for a PR that is never merged. Costs one more step in the main session's merge checklist.
- **Recommendation note (interviewer's):** Fix the drop in review() so nits survive to the script's result, and add the filing to the main session's post-merge steps in worktrees.md. The bead only exists for merged PRs.
- **Origin:** interviewer · accepted recommendation

<a id="nit-bead-granularity"></a>
### Follow-up beads: one per PR or one per nit

- **Decision:** One bead per PR listing all nits with file:line
- **Why (interviewer's case):** Matches current hand practice and keeps the backlog readable. Costs the ability to close nits individually.
- **Recommendation note (interviewer's):** The existing PR-nits beads already work this way and the pilot tickets are three of them. Keep one per PR; a nit that turns out to be a defect gets its own bead when someone picks the nits bead up.
- **Origin:** interviewer · accepted recommendation

<a id="nit-bead-priority"></a>
### Priority and labels on the nits bead

- **Decision:** Priority 3, label pr-nits, title 'PR #N nits: <ticket id>'
- **Why (interviewer's case):** Low enough not to crowd real work, findable by label, and the title links back. Costs nothing new.
- **Recommendation note (interviewer's):** A fixed low priority with a label gives one query for a nits sweep day and keeps the bead out of the way otherwise.
- **Origin:** interviewer · accepted recommendation

<a id="pilot-success"></a>
### What the pilot must show for the changes to stay

- **Decision:** Both of the above
- **Why (interviewer's case):** Value and cost together. Harder to meet on only three tickets.
- **Recommendation note (interviewer's):** Keep the changes if the tool found at least one survivor a human reviewer did not, the evidence re-ran, and the per-ticket cost stayed within the known range. If the tool found nothing on three test-coverage tickets, that is itself the answer.
- **Origin:** interviewer · accepted recommendation

<a id="revert-method"></a>
### One revert mechanism for the red run

- **Decision:** Patch round trip: git diff main...HEAD -- <src files> > /tmp/<bead>.patch, git apply -R, run test, git apply
- **Why (interviewer's case):** Reverts only source files so the new test stays in place, is scriptable, and the reviewer runs the identical two commands. Costs a conflict if the builder edits between diff and apply.
- **Recommendation note (interviewer's):** Name the patch round trip in builder, fix and reviewer templates with the exact commands, scoped to source paths so the test file stays. The reviewer then re-runs the same two lines and compares output.
- **Origin:** interviewer · accepted recommendation

<a id="screenshot-storage"></a>
### Where UI screenshots live so the PR body can show them

- **Decision:** Keep the PNGs outside git, in the main checkout's .scratch/evidence/<bead>/ (by absolute path, not the worktree's .scratch, which is deleted when the worktree is pruned after merge; .scratch/ is ignored through .git/info/exclude). Nothing is committed. The PR body names that path and the playwright-core command that regenerates the images; the reviewer regenerates them rather than trusting them.
- **Origin:** interviewer · own answer

<a id="evidence-retention"></a>
### How long .scratch/evidence/<bead>/ is kept after merge

- **Decision:** Keep until the nits bead for that PR is closed, then delete in the main session
- **Why (interviewer's case):** Anyone working the follow-up bead can still see the before and after. Costs a line in the bead-closing step.
- **Recommendation note (interviewer's):** Tie the lifetime to the artefact that still references it. The reviewer regenerates anyway, so losing the images later costs nothing.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Who files the nits bead: the workflow's last step or the main session after merge](#nit-bead-filer), [Where UI screenshots live so the PR body can show them](#screenshot-storage)

<a id="severity-scale"></a>
### Severity scale for review findings

- **Decision:** Three levels: blocker, should-fix, nit
- **Why (interviewer's case):** Should-fix goes into the fix round only if a blocker already forces one, otherwise to the follow-up bead. Costs one more judgment per finding and a routing rule.
- **Origin:** interviewer · another offered option

<a id="evidence-rerun-failure"></a>
### What a non-reproducing Evidence line means for the verdict

- **Decision:** Nit if the test passes with the change, blocking only if it also passes with the change reverted
- **Why (interviewer's case):** Distinguishes stale quotes from weak tests. Costs the reviewer a second run to tell them apart.
- **Recommendation note (interviewer's):** A test that passes with the change reverted is the real failure and must block. A stale quote with a correct test is a nit about the PR body.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Severity scale for review findings](#severity-scale)

<a id="should-fix-routing"></a>
### Where a should-fix finding goes

- **Decision:** Listed in the verdict with evidence; fixed in a fix round only if a blocker already forces one; otherwise goes to the nits bead; never blocks alone
- **Why (interviewer's case):** Gives the builder a chance to fix it cheaply when a round is happening anyway, without spending one of the two rounds on it. Costs a slightly longer verdict comment and a bead that mixes should-fix and nit items.
- **Recommendation note (interviewer's):** The level earns its keep only if it changes behaviour somewhere: here it changes what the fix round includes when a round happens, and it carries an evidence command so the bead entry is actionable. The verdict stays pass when only should-fix and nits remain.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Severity scale for review findings](#severity-scale)

<a id="fix-round-evidence-update"></a>
### What the fix round owes the PR body

- **Decision:** Re-quote every Evidence entry whose test or ranges changed, add an entry for each new test, and a 'Round N' line under Merge danger if blast radius changed
- **Why (interviewer's case):** The reviewer re-runs evidence in round two, so stale quotes would surface as nits anyway; doing it in the fix round avoids that noise. Costs the fixer the patch round trip again for touched entries.
- **Recommendation note (interviewer's):** Touched entries only, with the same patch round trip the builder used, so the PR body stays true without re-running everything.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [How the builder maps each acceptance line to line ranges](#acceptance-range-mapping), [One revert mechanism for the red run](#revert-method), [Where a should-fix finding goes](#should-fix-routing)

<a id="nit-bead-contents"></a>
### What the follow-up bead records per item

- **Decision:** Level, file:line, one-line fix, evidence command for should-fix, and 'addressed in round N' when it was
- **Why (interviewer's case):** Someone picking up the bead months later can reproduce a should-fix and skip what was already fixed. Costs the main session a small formatting step from the workflow result.
- **Recommendation note (interviewer's):** Format the entries in the main session from the workflow's returned arrays, so the bead reads like the existing PR-nits beads but with the level and evidence attached.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Follow-up beads: one per PR or one per nit](#nit-bead-granularity), [Where a should-fix finding goes](#should-fix-routing)

<a id="review-schema-shape"></a>
### Shape of the workflow's REVIEW schema with three levels and evidence

- **Decision:** One findings array, each entry with level (blocker | should-fix | nit), file, line, claim, evidence command (required for blocker and should-fix), optional 'equivalent mutant' note
- **Why (interviewer's case):** One shape to validate and route; the verdict and the bead are filters over it. Costs a schema and template change in lockstep, and the existing nits array goes away.
- **Recommendation note (interviewer's):** A single typed entry with a level field makes routing a filter and keeps the bead formatting trivial. The reviewer template emits the same fields it already uses, plus level and evidence.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Who files the nits bead: the workflow's last step or the main session after merge](#nit-bead-filer), [Severity scale for review findings](#severity-scale), [Where a should-fix finding goes](#should-fix-routing)

<a id="stryker-cap"></a>
### Stryker cap per PR: wall clock, mutant count, and what the reviewer pays

- **Decision:** 10 minutes wall clock, 100 mutants, concurrency 2, perTest coverage
- **Why (interviewer's case):** Fits a diff of a few hundred lines, leaves headroom for a machine under load, and keeps the reviewer's input small. Costs nothing on token side beyond the survivor table. A larger diff gets truncated and the truncation is reported.
- **Recommendation note (interviewer's):** Set a cap the script enforces and record per ticket what the actual run took, so the pilot produces the number the proposal lacks. Pass the reviewer only survivors with file, line, mutator and the test run status.
- **Origin:** interviewer · accepted recommendation

<a id="stryker-overrun"></a>
### What happens when Stryker hits the cap or fails to run

- **Decision:** Report the overrun as a non-blocking note and skip the gate
- **Why (interviewer's case):** Keeps the loop moving and records the miss in the benchmark. Costs a hole in the gate that a large PR can walk through.
- **Recommendation note (interviewer's):** During the pilot an overrun is data, not a block. Record it in the benchmark and let the reviewer say so in the verdict; tighten once three tickets show what a normal run costs.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Mutation result: gate, report, or gate only on acceptance-covered lines](#mutation-role), [Stryker cap per PR: wall clock, mutant count, and what the reviewer pays](#stryker-cap)

<a id="stryker-rerun-in-fix-round"></a>
### Whether Stryker runs again after a fix round

- **Decision:** Re-run on the full PR diff against main, same cap, before each review round
- **Why (interviewer's case):** Round two judges the code it is actually reviewing and sees whether the fix killed the survivors. Costs up to another ten minutes per round.
- **Recommendation note (interviewer's):** The step is deterministic and capped, so run it before every review round on the whole PR diff. The benchmark records each run's time so you see the real per-ticket cost including rounds.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Who runs Stryker: the tests lens, a separate mutation critic, or a deterministic workflow step](#mutation-runner), [Stryker cap per PR: wall clock, mutant count, and what the reviewer pays](#stryker-cap), [What happens when Stryker hits the cap or fails to run](#stryker-overrun)

<a id="stryker-setup"></a>
### Where the Stryker dependency and config live

- **Decision:** devDependencies in grill-room/package.json, stryker.config.mjs in grill-room, an npm script test:mutate that takes --mutate ranges
- **Why (interviewer's case):** Reviewer, builder and a hand loop all run the same command from the repo. Costs two dev dependencies and a config in the app folder.
- **Recommendation note (interviewer's):** The reviewer template already has to document the command for a hand loop, so it must be a repo script. Pin the versions and keep the config minimal: vitest runner, perTest coverage, concurrency and timeout from the cap, JSON reporter to .scratch.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Who runs Stryker: the tests lens, a separate mutation critic, or a deterministic workflow step](#mutation-runner), [Stryker cap per PR: wall clock, mutant count, and what the reviewer pays](#stryker-cap)

<a id="survivor-finding-severity"></a>
### Severity assigned to a surviving mutant

- **Decision:** Blocking on acceptance-covered lines, nit elsewhere, reviewer may downgrade with a stated reason
- **Why (interviewer's case):** Follows the role decision directly. Costs a stated reason per downgrade, which is what makes the verdict auditable.
- **Recommendation note (interviewer's):** Default follows the role decision; a downgrade must quote the mutant and say why no test could kill it.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Mutation result: gate, report, or gate only on acceptance-covered lines](#mutation-role), [Severity scale for review findings](#severity-scale)

<a id="tdd-evidence"></a>
### TDD proof: the red run in Evidence, or commits showing the test before the change

- **Decision:** Red run quoted in Evidence is enough
- **Why (interviewer's case):** The reviewer re-runs it, so it proves the same thing the commit order would. Costs nothing and tolerates squashed or reordered commits.
- **Recommendation note (interviewer's):** A quoted red run that the reviewer reproduces proves the test detects the change. Commit archaeology proves ritual, and mutation testing covers the strength question better than ordering ever did.
- **Origin:** interviewer · accepted recommendation

<a id="test-only-pr-scope"></a>
### What Stryker mutates when the PR changes only tests

- **Decision:** Mutate the source lines the new or changed tests cover, from a vitest coverage run of only those test files
- **Why (interviewer's case):** Measures exactly what the ticket claims to add: whether the new tests kill anything. Costs a coverage run before Stryker and a small script to turn coverage into ranges.
- **Recommendation note (interviewer's):** Without this rule the pilot cannot produce a single surviving mutant. Coverage from the changed test files, capped as before, is the honest scope for a test-only PR and is also the right scope for the acceptance-line mapping on those tickets.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Mutation result: gate, report, or gate only on acceptance-covered lines](#mutation-role), [How the diff scope is expressed to Stryker](#mutation-scope)
