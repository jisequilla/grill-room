# Decisions: Export by lifetime + ADR drafts

Generated by the Grill Room export from this session's settled design tree.

## Decisions

<a id="p1-file-split"></a>
### Which files are durable and which are working?

- **Decision:** As stated, ADR drafts count as durable
- **Why (interviewer's case):** Buys a clean rule: durable files explain the built system, working files drive the build. Costs nothing new beyond classifying ADR drafts, which are clearly explanatory.
- **Recommendation note (interviewer's):** Keep decisions.md durable: it is the full record, ADRs are the significant subset with a different lifecycle. An ADR draft is an explanation of the system, so it is durable by the same rule.
- **Origin:** interviewer · accepted recommendation

<a id="p1-scope-sequencing"></a>
### Ship Part 1 and Part 2 together or as two deliveries?

- **Decision:** Part 1 first, then Part 2 on top
- **Why (interviewer's case):** Buys a proven two-root export before the ADR writer relies on it, and keeps each ticket reviewable. Costs one extra round trip before ADRs appear.
- **Recommendation note (interviewer's):** The two-root layout is the foundation, and it touches the guard and manifest that Part 2 must trust. Land it, export once for real, then build ADRs on it.
- **Origin:** interviewer · accepted recommendation

<a id="p1-settings-shape"></a>
### Project settings: how are the two destinations configured?

- **Decision:** Two explicit folders, both configurable
- **Why (interviewer's case):** Buys symmetry: every validation, visibility and containment check runs identically over both roots and the defaults are just values. Costs a schema migration and two fields in the settings UI.
- **Recommendation note (interviewer's):** Symmetry is worth the migration: the export plan, the edited-file guard and the visibility checks already work per path, so two roots configured the same way keeps them one code path. Renaming the existing field avoids the lie of a name that no longer says what it holds.
- **Origin:** interviewer · accepted recommendation

<a id="p1-cross-root-paths"></a>
### How do HANDOFF.md and briefs reference files in the other root?

- **Decision:** Repo-root-relative paths everywhere
- **Why (interviewer's case):** Buys links that survive the working folder moving or being deleted and are readable from any worktree. Costs links that do not resolve in a Markdown preview opened from inside the folder.
- **Recommendation note (interviewer's):** Agents and humans both read these from the repo root; stable paths beat clickable previews.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Which files are durable and which are working?](#p1-file-split), [Project settings: how are the two destinations configured?](#p1-settings-shape)

<a id="p1-manifest-roots"></a>
### One manifest spanning two roots, or one per root?

- **Decision:** Two manifests, one per root
- **Why (interviewer's case):** Buys durable files keeping their own hash record after the working folder is deleted. Costs two files to read and reconcile on every export.
- **Recommendation note (interviewer's):** The guard needs the previous hash to protect hand edits, and the durable root outlives the working one, so each root keeps its own record.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Which files are durable and which are working?](#p1-file-split), [Project settings: how are the two destinations configured?](#p1-settings-shape)

<a id="p1-cleanup-action"></a>
### Does Grill Room offer the working-folder cleanup, or is it manual?

- **Decision:** Manual deletion; Grill Room notices on next open and marks the session's export as retired
- **Why (interviewer's case):** Buys no destructive action inside Grill Room and no new permission surface. Costs the user doing it by hand and a detection path for a missing working root.
- **Recommendation note (interviewer's):** Deletion is a repo commit the owner should make; Grill Room only needs to cope gracefully when the working root is gone.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [One manifest spanning two roots, or one per root?](#p1-manifest-roots)

<a id="p1-migration"></a>
### Migrating existing projects from one exportFolder

- **Decision:** Migrate by where the existing exportFolder points. If it sits under docs/ (e.g. ngine-monitor's docs/specs), it becomes the durable root and the working root defaults to .grill-room. Otherwise (e.g. .scratch) it becomes the working root and the durable root defaults to docs/specs. Re-run the visibility check on both roots on next open. Validation refuses two roots that are the same folder or nested one inside the other, so a migration can never produce durable == working.
- **Origin:** interviewer · own answer
- **Depends on:** [Project settings: how are the two destinations configured?](#p1-settings-shape)

<a id="p1-reexport-after-retire"></a>
### What does re-export do once the working folder has been deleted?

- **Decision:** Refuse, with an explicit override
- **Why (interviewer's case):** Buys protection against a stale session resurrecting tickets that already merged. Costs one extra confirmation for the rare legitimate re-export.
- **Recommendation note (interviewer's):** Retired means the build is done; the export should say so and make the owner ask twice before it puts tickets back.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Does Grill Room offer the working-folder cleanup, or is it manual?](#p1-cleanup-action)

<a id="p1-settings-naming"></a>
### Naming the new setting against the session docsFolder

- **Decision:** Name by lifetime: durableExportFolder / workingExportFolder
- **Why (interviewer's case):** Buys names that say what the split means and cannot be confused with the read-only docsFolder. Costs slightly longer identifiers.
- **Recommendation note (interviewer's):** Name the fields for the lifetime they hold, not the folder they default to.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Project settings: how are the two destinations configured?](#p1-settings-shape)

<a id="p1-shared-slug"></a>
### Do both roots share the same session folder name?

- **Decision:** One shared slug under both roots
- **Why (interviewer's case):** Buys an obvious pairing: anyone can find the working half of a spec by name, and a cleanup of `.grill-room/<slug>/` is unambiguous. Costs a rename in one root if the session is retitled, which must propagate to both.
- **Recommendation note (interviewer's):** The two halves are one export; the same leaf name under both roots is the cheapest way to say so, and retitling is already a rare event handled by the manifest.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Project settings: how are the two destinations configured?](#p1-settings-shape)

<a id="p1-visibility-policy"></a>
### Visibility policy per root: warn or refuse when a root is gitignored?

- **Decision:** Refuse export if the durable root is ignored; warn if the working root is
- **Why (interviewer's case):** Buys a hard guarantee that durable docs are visible. Costs blocking an export until the owner fixes .gitignore.
- **Recommendation note (interviewer's):** The owner's ruling was about hidden output; durable output hidden is a failure, working output hidden is a choice worth a warning.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Project settings: how are the two destinations configured?](#p1-settings-shape)

<a id="p2-destination"></a>
### Where do draft ADRs land?

- **Decision:** Grill Room writes no ADR files. The repo writes its own ADRs, in its own convention and numbering; Grill Room only suggests them. The export carries, for each ADR-worthy decision, an ADR-shaped suggestion (Context from the question and evidence, Decision from the answer, Alternatives from the unchosen options and superseded answers, Consequences, the tickets that implement it) in a durable file, and the HANDOFF tells the building session to write the repo's ADRs from those suggestions. So Grill Room never writes into a decisions folder it does not own, never allocates numbers, and needs no manifest entry for ADRs.
- **Origin:** interviewer · own answer
- **Depends on:** [Which files are durable and which are working?](#p1-file-split), [Project settings: how are the two destinations configured?](#p1-settings-shape)

<a id="p2-acceptance-guard"></a>
### What acceptance means to the export guard

- **Decision:** Not applicable: Grill Room writes no ADR files (settled in p2-destination). Suggestion files are Grill Room's own durable files, guarded by the existing hash rule like spec.md. Acceptance happens in the repo's own ADR file, which Grill Room never writes or tracks, so the guard needs no acceptance rule.
- **Origin:** interviewer · own answer
- **Depends on:** [Where do draft ADRs land?](#p2-destination)

<a id="p2-granularity"></a>
### One ADR per decision, or bundled?

- **Decision:** One decision per ADR
- **Why (interviewer's case):** Buys clean supersession and amendment: each ADR has one Decision line and one thing that can later be reversed. Costs more files and possibly thin ADRs when a parent and child are really one choice.
- **Recommendation note (interviewer's):** The design tree already gives each decision a single `supersededById`, so one decision per ADR keeps the tree and the documents isomorphic. Thin ADRs are a marking problem, not a bundling problem: if a child is not costly to reverse on its own, do not mark it.
- **Origin:** interviewer · accepted recommendation

<a id="p2-amends"></a>
### Expressing that a draft amends or supersedes an existing repo ADR

- **Decision:** Draft carries 'Amends: NMON-012' derived from the superseded repo decision's citation; the existing ADR is not touched
- **Why (interviewer's case):** Buys provenance without editing files Grill Room does not own. Costs the old ADR not knowing it was amended until acceptance.
- **Recommendation note (interviewer's):** A proposed ADR may claim to amend; only acceptance should touch the accepted one.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Where do draft ADRs land?](#p2-destination), [One ADR per decision, or bundled?](#p2-granularity)

<a id="p2-handoff-convention"></a>
### What does HANDOFF tell the builder about the repo's ADR convention?

- **Decision:** Detect folder, numbering and template; state them in HANDOFF
- **Why (interviewer's case):** Buys a builder that can write the ADR without exploring, and a checkable scout fact. Costs heuristic detection that will sometimes guess a pattern wrong, so it must be phrased as a hint.
- **Recommendation note (interviewer's):** Detection is cheap and a wrong guess is only a hint the builder can override; leaving it out puts the exploration back on every build.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Where do draft ADRs land?](#p2-destination)

<a id="p2-marking"></a>
### Who marks a decision ADR-worthy, and when?

- **Decision:** Interviewer proposes, user overrides
- **Why (interviewer's case):** Buys the judgement being made when the context is freshest, with the rationale already in hand. Costs a new field in the proposal schema and a UI affordance to flip it.
- **Recommendation note (interviewer's):** Mark at proposal time, because the interviewer can say why it thinks the decision is costly to reverse, and that sentence is the seed of the Context section. The user keeps the final say with a toggle on the settled decision.
- **Origin:** interviewer · accepted recommendation

<a id="p2-consequences"></a>
### Where does the Consequences section come from?

- **Decision:** Interviewer writes consequences when it proposes the ADR-worthy flag, stored on the decision, user-editable
- **Why (interviewer's case):** Buys consequences written with the reasoning fresh. Costs a field and a slightly longer proposal.
- **Recommendation note (interviewer's):** Consequences are a judgement, so capture them when the judgement is made.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Who marks a decision ADR-worthy, and when?](#p2-marking)

<a id="p2-marking-scope"></a>
### Which decisions can carry the ADR-worthy flag?

- **Decision:** Any settled decision, origin-aware defaults
- **Why (interviewer's case):** Buys ADRs for the decisions that most often are architectural, which are frequently the ones the user typed in or the scout recovered. Costs a flag on three proposal shapes instead of one.
- **Recommendation note (interviewer's):** The amends case only works if a repo decision can be marked, and user-added decisions are often the most significant ones. One flag, three defaults.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Who marks a decision ADR-worthy, and when?](#p2-marking)

<a id="p2-no-convention"></a>
### What happens when the scout finds no ADR convention?

- **Decision:** Not applicable: Grill Room writes no ADR files (settled in p2-destination). Suggestions are always written in Grill Room's own built-in shape (Status, Context, Decision, Alternatives, Consequences, Tickets, Amends) under the durable spec folder, whatever the repo's convention; when the scout finds no convention, HANDOFF says so and the repo's owner decides where ADRs go.
- **Origin:** interviewer · own answer
- **Depends on:** [Where do draft ADRs land?](#p2-destination)

<a id="p2-numbering"></a>
### Reserving ADR numbers in the repo's sequence

- **Decision:** Not applicable: Grill Room writes no ADR files (settled in p2-destination). Grill Room reserves and records no numbers. HANDOFF may state the next free number as a hint (see p2-handoff-convention); the builder takes the real number when it writes the ADR.
- **Origin:** interviewer · own answer
- **Depends on:** [Where do draft ADRs land?](#p2-destination)

<a id="p2-decisions-md-link"></a>
### Does decisions.md point at the ADR draft for each ADR-worthy decision?

- **Decision:** decisions.md marks each ADR-worthy entry as ADR-worthy (with its Amends target when there is one) but carries no path: Grill Room never knows the real ADR's path or number, and a link to the suggestion file would break when the working folder is deleted.
- **Origin:** interviewer · own answer
- **Depends on:** [Where do draft ADRs land?](#p2-destination), [Reserving ADR numbers in the repo's sequence](#p2-numbering)

<a id="p2-suggestion-file"></a>
### Where do the ADR suggestions live in the durable export?

- **Decision:** One file per suggestion under adr/
- **Why (interviewer's case):** Buys a builder that copies a file, renames it into the convention, and flips Status: the least from-scratch work. Costs a folder of files that look like ADRs but are not, which a reader may mistake for the real record.
- **Recommendation note (interviewer's):** The whole point is to remove the from-scratch step; a per-decision file that already has the ADR shape makes accepting one a copy and a rename. Name the folder to say what it is, not `adr/`, so nobody mistakes it for the record.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Which files are durable and which are working?](#p1-file-split), [Where do draft ADRs land?](#p2-destination)

<a id="p2-suggestion-folder-name"></a>
### What is the suggestions folder called?

- **Decision:** adr-suggestions/, as recommended, but under the working root: .grill-room/<slug>/adr-suggestions/<decision-key>.md.
- **Origin:** interviewer · own answer
- **Depends on:** [Where do the ADR suggestions live in the durable export?](#p2-suggestion-file)

<a id="p2-ticket-links"></a>
### How does an ADR know which tickets build it?

- **Decision:** Explicit decision keys on issues
- **Why (interviewer's case):** Buys an exact, checkable link in both directions and an ADR that can name its tickets. Costs a new field on issues and one more thing the interviewer must fill.
- **Recommendation note (interviewer's):** An explicit list of implemented decision keys on each issue is small, checkable at export, and gives the ADR its Tickets section and the ticket its ADR reference for free.
- **Origin:** interviewer · accepted recommendation

<a id="p2-adr-ticket"></a>
### Is writing the repo's ADRs its own ticket, or a HANDOFF instruction?

- **Decision:** One generated ADR ticket, sequenced last
- **Why (interviewer's case):** Buys a visible, trackable piece of work that closes when the record is written. Costs one more issue file and a rule for its position in the sequence.
- **Recommendation note (interviewer's):** Untracked instructions get dropped; a last ticket that lists the suggestions and closes on the record being written is how NMON-019 actually happened, minus the from-scratch part.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Where do draft ADRs land?](#p2-destination), [How does an ADR know which tickets build it?](#p2-ticket-links)

<a id="p2-adr-ticket-body"></a>
### What does the generated ADR ticket contain?

- **Decision:** Self-contained ticket with a done condition
- **Why (interviewer's case):** Buys a ticket a builder can execute without HANDOFF and a reviewer can check. Costs duplicating the convention hint in two working files that must agree.
- **Recommendation note (interviewer's):** Tickets are the unit of work the builder picks up; this one should read like the others, with its own done condition, even if HANDOFF repeats the hint.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [What does HANDOFF tell the builder about the repo's ADR convention?](#p2-handoff-convention), [Is writing the repo's ADRs its own ticket, or a HANDOFF instruction?](#p2-adr-ticket)

<a id="p2-orphan-checks"></a>
### What does export do with unlinked ADR-worthy decisions and unlinked issues?

- **Decision:** Warn on an ADR-worthy decision with no implementing ticket, and still export its ADR suggestion with an empty Tickets list; issues with no decision keys are fine. (Grill Room suggests ADRs; it does not write them.)
- **Origin:** interviewer · own answer
- **Depends on:** [Who marks a decision ADR-worthy, and when?](#p2-marking), [How does an ADR know which tickets build it?](#p2-ticket-links)

<a id="p2-suggestion-lifecycle"></a>
### What happens to a suggestion once the repo's ADR exists?

- **Decision:** Suggestions are working files, not durable ones: they live in the working root at .grill-room/<slug>/adr-suggestions/<decision-key>.md and are deleted with the rest of the build's working files. The repo's own ADR is the only durable record once written, so there is never a duplicate, no 'deleted on purpose' guard rule, and no hand edit to Grill Room's files. This amends p1-file-split: ADR suggestions are working, not durable. The generated 'Record ADRs from suggestions' ticket must close before the working folder is deleted; the working-folder cleanup (manual, per p1-cleanup-action) should say so in HANDOFF.
- **Origin:** interviewer · own answer
- **Depends on:** [Where do the ADR suggestions live in the durable export?](#p2-suggestion-file), [Is writing the repo's ADRs its own ticket, or a HANDOFF instruction?](#p2-adr-ticket)

<a id="p2-decisions-md-consequences"></a>
### Does decisions.md keep the Consequences once suggestions are deleted?

- **Decision:** Render Consequences in decisions.md for ADR-worthy entries
- **Why (interviewer's case):** Buys a durable record that survives a skipped ADR ticket and a re-export that can regenerate suggestions from the same source. Costs slightly longer decisions.md entries for the marked subset only.
- **Recommendation note (interviewer's):** The consequences were a judgement made during the interview; the durable record should hold it regardless of whether the builder ever writes the ADR.
- **Origin:** interviewer · accepted recommendation
- **Depends on:** [Where does the Consequences section come from?](#p2-consequences), [Does decisions.md point at the ADR draft for each ADR-worthy decision?](#p2-decisions-md-link), [What happens to a suggestion once the repo's ADR exists?](#p2-suggestion-lifecycle)
